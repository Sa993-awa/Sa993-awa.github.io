```Python

from abc import ABC,abstractmethod

class NotificationService(ABC):         #Interface (NotificationService)
    @abstractmethod
    def send_notification(self,user,message):
        pass



class EmailService:
    def send_email(self, user, message):
        print(f"Sending email to {user}: {message}")

class SMSService(NotificationService):                  #Add More Services
    def send_notification(self, user, message):
        print(f"Sending SMS to {user}: {message}")        


class UserManager:
    def __init__(self,notifier:NotificationService):
        self.notifier = notifier

    def register_user(self, user):
        self.notifier.send_notification(user, "Welcome!")
```


```pyhton
from unittest.mock import Mock

def test_register_user_sends_welcome_notifiaction():
    mock_notifier=Mock(spec=NotificationService)
    manager=UserManager(mock_notifier)

    manager.regsiter_user("Sally@uniuk.com")
    mock_notifier.send_notfication.assert_called_once_with("Sally@uniuk.com","Welcome!")
```


🟢 The initial code UserManager had two main problem. First, it was tightly coupled to EmailService. Second, it was hard to test because it always tried to send a real email.

Refactoring this code by a few steps: create an interface with NotificationService and made EmailService implement it. Then change UserManager so the notification service is injected into it instead of being created inside the class . This means that as class should receive what it needs from outside rather than building it itself, Which is the essential core idea of Dependency injection.

The SOLID Principle applied in this code. Such as SRP where the UserManager manages user registration and the notification classes are responsible for sending notification. And OPC applied by adding SMSService(NotificationService) without modifying UserManager. Also DIP when UserManager depends on the Notificationservice abstraction rather than directly relying on EmailService.

Using Dependency Injection makes the class less dependent on each other, which makes the code easier to maintain, extend and test. It also makes testing easier because real services can be replaced with simple mock objects.
