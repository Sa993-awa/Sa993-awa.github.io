### Factory method Design Pattern

```python
class Car (ABC):
    @abstractmethod
    def drive(self):
        pass

class Sedan (Car):
    def drive(self):
        print("Drive safely with Sedan!, Better fuel economy!,Easier parking!")

class SUV (Car):
    def drive (self):
        print("Stay calm!,Flexible seating,Sports gear")


class Hatchback(Car):
     def drive (self):
         print("Safety features,environmental benefits")  

class CarFactory(ABC):
    @abstractmethod
    def create_car(self):
        pass 


    def create_car(self):     
        car =self.create_car
        car.drive()


class SedanFactory(CarFactory):
    def create_car(self):
        return Sedan()     



class SUVFactory(CarFactory):
    def create_car(self):
        return SUV()       


class HatchbackFactory(CarFactory):
    def create_car(self):
      return Hatchback() 


if __name__ == "__main__":
     Factories = [SedanFactory(), SUVFactory() ,HatchbackFactory()]

     for factory in Factories:
          car = factory.create_car()
          car.drive()
```

🟢 The Factory Method is a creational design pattern that lets a program create objects without specifying their concrete classes directly, making it reusable across different parts of an application. In this car manufacturing system, I designed a system where different types of cars Sedan, SUV, and Hatchback  can be created while keeping the main program independent of any specific car class.
First, I defined a Car interface class with an abstract method drive(). This acts as the common interface and ensuring that every concrete car  implements the same behaviour. The three concrete classes Sedan, SUV, and Hatchback each inherit from Car and provide their own implementation of drive(), printing a message describing that car type.
Next, I defined the CarFactory Abstract Class with the factory method create_car(). This method is the main part of the pattern, rather than creating cars directly, the base factory declares that its subclasses are responsible for producing a car. Each concrete factory  SedanFactory, SUVFactory, and HatchbackFactory overrides create_car() and returns its own specific car object. The Factory Method Pattern is ideal for this because it delegates object creation to subclasses.
Finally, I demonstrated  the Factory Method Pattern in the main program using the factories. The client loops through each factory, calls create_car() to obtain a car, and calls drive() on it. 
Importantly,The client code depends only on the abstract Car and CarFactory. it never references a concrete car class.
The key advantage is scalability; if the company later introduces a new car type—such as "Mercedes"—I would only need to create a new "Mercedes" class and a corresponding factory, without modifying any part of the existing code. This separation between object creation and application logic makes the system easier to maintain and extend, thereby supporting the "Open/Closed Principle."



### 💬 Unit Reflection
In this unit, I learned how the Factory Method pattern lets a program create objects without depending on their concrete classes. I built a car manufacturing system where different car types — Sedan, SUV, and Hatchback — are created while keeping the main program independent of any specific car class.

I first defined a Car interface with an abstract drive() method, so every concrete car shares the same behaviour. The Sedan, SUV, and Hatchback classes each implement drive() in their own way. I then created a CarFactory abstract class with the factory method create_car(), and each concrete factory (SedanFactory, SUVFactory, HatchbackFactory) overrides it to return its own car. The client loops through the factories, calls create_car(), and then drive(), depending only on the abstract Car and CarFactory rather than any concrete class.

The main advantage I saw was scalability: to add a new car type like "Mercedes", I would only write a new class and factory without changing existing code, which supports the Open/Closed Principle. Sarcar (2022) explains this well; although he uses Java and focuses on the related Abstract Factory pattern (a "factory of factories"), his point that these factories promote loose coupling by reducing dependencies on concrete classes transferred directly to my Python work.

Overall, this unit showed me how delegating object creation to subclasses keeps code easier to maintain and extend, and gave me a clearer understanding of how creational patterns support clean, flexible design.
