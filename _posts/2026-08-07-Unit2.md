### Refactored Code Steps (SOLID Principles)

```Python

from abc import ABC, abstractmethod

# A class should have only one reason to change.

class Order:                                             # Single Responsibitiy Principle

    def __init__ (self):
        self.items =[]

    def add_item(self,item):                              #Add a new item to the basket  cart
        self.items.append(item)

    def calculate_total(self):                            #Calculate the total price of all items in the cart
        return sum(item.price for item in self.items)
    
#Checkout uses abstraction instead of a specific payment class (DIP).

    def checkout(self,payment_method,discount_method):  
        total = self.calculate_total()
        total=discount_method.apply_discount(total)        #Apply discount befor payment
        payment_method.pay(total)
                                                           #Process the selected payment method 


#open / closed Principle
class  PaymentMethod(ABC):                                     #Dependency Inversion Principle
                                                                 #PaymentMethod provides a commen abstraction for all payment methods   
                  
    @abstractmethod
    def pay(self,amount):
        pass


class CreditCardProcessor(PaymentMethod):                    #Liskov Substitution Principle
                                                             #CreditCardProcessor can be used wherever PaymentMethod is expected
    def pay(self,amount):
        print(f"Processing credit card payment for £{amount}") 
      

class PaypalProcessor(PaymentMethod):

    def pay(self,amount):
        print(f"Processing Paypal payment for £{amount}") 

class CryptoPayment(PaymentMethod):

    def pay(self,amount):
        print(f"Processing Crypto payment for £{amount}")


class Items:                                             #Add real product to the cart

    def __init__(self,name,price):
        self.name=name
        self.price=price


class DiscountMethod(ABC):                                 #Discount apply.

    @abstractmethod
    def apply_discount (self,total):
        pass

class NoDiscount (DiscountMethod) :                       #No Discoutn appl.

    def apply_discount (self,total):
        return total

class PercentageDiscount(DiscountMethod):

    def __init__(self,percentage):
        self.percentage = percentage   


    def apply_discount(self,total):
        return total -(total*self.percentage/100)



 #Create some shopping items.
order=Order()                                               

item1= Items("Table",600)                         
item2= Items("chairs",400)

#Add items to the order.
order.add_item(item1)
order.add_item(item2)

#Apply a 30% discount
discount=PercentageDiscount(30)

#Select Creditcard as the payment method 
payment=CreditCardProcessor()

 #checkout and process the payment
order.checkout(payment,discount)

```


🟢 In this code, I created an Order class to manage shopping items using SOLID Principle. It includes add items, calculate the total price, and process checkout applying the Single Responsibility Principle.  I used abstraction with PaymentMethod and DiscountMethod so different payment and discount options can be added and removed easily. Then  I created separate classes for Credit Card, PayPal, and Crypto payments, following the Open/Closed which is open for extension and close for modification and Liskov Substitution Principles. I also used Dependency Inversion by making Order depend on the abstract payment and discount methods rather than specific classes. This exercise helped me to understand SOLID Principle and improved my writing in codes to be more cleaner and flexible.  



### 💬 Unit Reflection

This week, I learned how the SOLID principles improve object-oriented programming by making code easier to maintain, extend, and understand. The practical exercises showed me that each principle has a specific purpose. The Single Responsibility Principle (SRP) taught me that each class should have only one responsibility in my shopping system, this meant separating the Order class, which manages cart items and totals, from the payment and discount logic, which I moved into their own PaymentMethod and DiscountMethod classes.   

During the seminar, the tutor asked if we had heard of SOLID before, and I said yes, since I had already looked through Unit 2 and covered part of it beforehand.

While building the shopping system, I ran into errors because I had not defined the DiscountMethod class before using it, and I had misspelled PercentageDiscount. As Python is case-sensitive, this caused a NameError. Reviewing the error messages and correcting the class definitions and spelling helped me understand debugging and the importance of careful, consistent naming.

I also strengthened my understanding of the Open/Closed Principle (OCP) through the basket/cart example. I removed one payment method, PaypalProcessor, from the code entirely, and the program still ran correctly because Order.checkout() depends only on the abstract PaymentMethod class, not on any specific payment type. This showed me that classes should be open for extension (adding new payment methods) but closed for modification _not needing to change Order itself_, which is the core idea behind OCP.

Sarcar (2022) explains these principles very clearly, and although he applies the code in Java, he addresses the ideas in a way that transferred well to my Python work.

In addition, Martin (2023) describes the OOP as:   

1\. Single Responsibility Principle (SRP): this principle states that a software module should be responsible to only one "actor." Since the person defining the input format differs from the person defining credit policy, combing these two aspects means that modifying one could disrupt the other. The solution relies in separating syntactic validation from semantic validation and placing each in an independent module.


2\. Open-Closed Principle (OCP): software should be extendable without needing to modify existing code. Each approach lets new behavior be added by writing new implementations rather than editing existing ones

3\. Liskov Substitution Principle (LSP): a subtype must be usable anywhere its base type is expected, without breaking the calling code's assumptions.

4\. Interface Segregation Principle (ISP): clients shouldn't be forced to depend on methods they don't use. And large interfaces should split into smaller interfaces.


5\. Dependency Inversion Principle (DIP): high-level policy shouldn't depend directly on low-level implementation details, both should depend on abstractions instead.

Overall, this unit increased my confidence in applying SOLID principles to write cleaner, more structured, and more maintainable Python code.
