#### During this unit, I developed my understanding of the SOLID principles and how they improve object-oriented programming by making code more organised, maintainable, and easier to extend. The practical activities helped me understand the purpose of each principle, especially the Single Responsibility Principle (SRP), which showed me the importance of giving each class a clear and specific responsibility. For example, separating order management from payment and discount processing made the code structure clearer and easier to manage.

#### Overall, this unit strengthened my confidence in applying SOLID principles in Python projects. I now have a better understanding of how these principles help create cleaner, more flexible, and maintainable software designs.

## The following code demonstrates a practical implementation of this concept in Python.

### Refactored Code Steps (SOLID Principles)

```Python

from abc import ABC, abstractmethod

# A class should have only one reason to change.

class Order:                                             # Single Responsibitiy Principle

    def __init__ (self):
        self.items =[]

    def add_item(self,item):                              # Add a new item to the basket  cart
        self.items.append(item)

    def calculate_total(self):                            # Calculate the total price of all items in the cart
        return sum(item.price for item in self.items)
    
# Checkout uses abstraction instead of a specific payment class (DIP).

    def checkout(self,payment_method,discount_method):  
        total = self.calculate_total()
        total=discount_method.apply_discount(total)        # Apply discount befor payment
        payment_method.pay(total)
                                                           # Process the selected payment method 


# open / closed Principle
class  PaymentMethod(ABC):                                     #Dependency Inversion Principle
                                                                 #PaymentMethod provides a commen abstraction for all payment methods   
                  
    @abstractmethod
    def pay(self,amount):
        pass


class CreditCardProcessor(PaymentMethod):                    #Liskov Substitution Principle
                                                             # CreditCardProcessor can be used wherever PaymentMethod is expected
    def pay(self,amount):
        print(f"Processing credit card payment for £{amount}") 
      

class PaypalProcessor(PaymentMethod):

    def pay(self,amount):
        print(f"Processing Paypal payment for £{amount}") 

class CryptoPayment(PaymentMethod):

    def pay(self,amount):
        print(f"Processing Crypto payment for £{amount}")


class Items:                                             # Add real product to the cart

    def __init__(self,name,price):
        self.name=name
        self.price=price


class DiscountMethod(ABC):                                 #Discount apply.

    @abstractmethod
    def apply_discount (self,total):
        pass

class NoDiscount (DiscountMethod) :                       # No Discoutn appl.

    def apply_discount (self,total):
        return total

class PercentageDiscount(DiscountMethod):

    def __init__(self,percentage):
        self.percentage = percentage   


    def apply_discount(self,total):
        return total -(total*self.percentage/100)



 #Create some shopping items.
order=Order()                                               

item1= Items("Table",600)                         
item2= Items("chairs",400)

#Add items to the order.
order.add_item(item1)
order.add_item(item2)

#Apply a 30% discount
discount=PercentageDiscount(30)

#Select Creditcard as the payment method 
payment=CreditCardProcessor()

 #checkout and process the payment
order.checkout(payment,discount)

```


#### In this code, I created an Order class to manage shopping items using SOLID Principle. It includes add items, calculate the total price, and process checkout applying the Single Responsibility Principle.  I used abstraction with PaymentMethod and DiscountMethod so different payment and discount options can be added and removed easily. Then  I created separate classes for Credit Card, PayPal, and Crypto payments, following the Open/Closed which is open for extension and close for modification and Liskov Substitution Principles. I also used Dependency Inversion by making Order depend on the abstract payment and discount methods rather than specific classes.
